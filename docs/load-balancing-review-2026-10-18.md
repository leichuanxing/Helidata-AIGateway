## 检查发现与修复

| 优先级 | 原有实现/缺口 | 处理 |
| --- | --- | --- |
| 高 | 读超时、响应损坏等不确定结果也会自动重试，可能重复计费 | 默认只允许明确可重试的错误；新增管理员显式风险开关，记录抑制原因 |
| 高 | 排序与容量预留分离，新增轮询若在轮询队列时推进计数会失真 | 将轮询、平滑加权、最少并发选择集成现有原子准入 Lua，预留与选择同事务 |
| 中 | 模型组没有独立策略、权重或重试/单次超时配置 | 增加持久化配置，保留历史组原有策略和模型后继顺序 |
| 中 | 故障重试直接遍历旧候选顺序，无法正确应用新的准入策略 | 切换前重新准入、重新授权/筛选，沿用容量、队列和模型合规约束 |
| 中 | 原有调用日志只通过最终账号列难以观察失败节点 | 从 attempts 汇总节点指标，并增加策略、映射、切换原因、重试次数快照 |
| 低 | 对话测试 CSS 残留字面量反引号 n，导致整站生产构建失败 | 修复该语法错误；没有修改对话业务行为 |
| 低 | 节点监控请求可能乱序覆盖最新页面 | 增加请求代次保护，防止旧响应覆盖新选择 |

复用未重建的模块：供应商/模型映射管理、模型组、模型授权、智能路由、内容合规、四级 Redis 并发租约、队列、Provider 健康/冷却、SSE 生命周期、调用日志和数据库连接池。

## 测试结果

- 后端全量 **114 项通过**，包含原有 105 项及新增 9 项负载均衡测试。
- 前端 TypeScript/Vue 生产构建通过；前端现有 **22 项通过**。
- 真实 Redis：100 个同时竞争的请求，容量为 7 时恰好准入 7 个；释放后为 0，排队请求可再次准入；过期租约清理通过。
- 算法：轮询顺序、公平轮转、排队不推进计数、平滑加权 40 次中 1:3 分配为 10:30、最少并发及优先级容量回退通过。
- 真实网关 HTTP：轮询、8 次加权调用 2:6、Chat/Responses/Messages 各普通响应和 SSE、连接失败切换、鉴权失败切换、连接检查后恢复、单次读超时显式切换、重试次数为 0、503 默认不重放与显式重试通过。
- SSE：上游输出后中断，仅一次上游调用、仅一条尝试日志，没有第二份回答；日志按异步终态等待后核验。
- 真实 PostgreSQL/Redis：故障冷却排除、到期单请求探测、探测成功清除故障并重新加入通过。
- 网关同时发起 8 个 HTTP 请求，单供应商并发上限 2 未被突破；完成后两节点租约均为 0；监控接口返回已落库请求数、成功率和耗时。
- 原有回归覆盖模型授权、网关安全、配额/统计、内容合规与智能路由联动、取消与资源清理、供应商配置、备份下载等；本次没有绕过这些检查。
- 停止隔离测试容器中的 API 后执行 `0032 → 0031 → 0032` 往返迁移：原有组字段、成员、供应商映射、授权、逻辑模型和调用日志逐行保持；回升后新增配置按默认值重建。这不是生产操作。
- 最后收紧权重的整数类型校验后，7 项相关测试重新通过；页面异步保护改动后，前端生产构建和 22 项测试重新通过。

上述协议测试使用本机可控上游服务，实际经过 HTTPX、网关、Redis 和 PostgreSQL，不代表已对外部所有供应商进行了兼容性认证。测试未产生供应商费用。

## 边界与遗留风险

1. 尚未上线生产，也未推送 GitHub。版本标签不移动。
2. 没有进行付费真实供应商调用、长时间压测、进程强杀混沌测试或多机 Redis 故障转移测试；已有单实例 Redis 故障关闭策略保持不变。
3. 上游不提供幂等保证时，无法保证跨节点恰好一次计费；不确定结果重试默认关闭。
4. 监控统计来自调用日志，存在流关闭后的短暂写入延迟；共享模型按模型/供应商汇总，不是独占的组归因统计。
5. 同一模型存在于多个授权组时选择最小组 ID；用户需要按文档规划逻辑模型名称，不能假设请求隐式选择任意模型组。
6. 页面完成编译与接口验证，尚未进行人工浏览器视觉验收；不把编译通过等同于所有屏幕尺寸已验收。
